# 脱敏说明（Desensitization notes）

这个仓库脱胎于一份**内部工程分析脚本**。内部脚本和开源仓库的差别不在技术，而在「能不能公开」。
本文记录：哪些东西被拿掉了、为什么、以及怎么验证。

## 一、结论先行

当前仓库里的**每一行代码都是为公开发布重写的**，没有从内部仓库拷贝文件。因此不存在「忘了删某段」的风险——
但仍建议每次发布前跑一遍 `scripts/scan-sensitive.sh` 做机械校验。

## 二、被移除的内容

| 类别 | 内部脚本里的形态 | 本仓库的处理 |
|---|---|---|
| 业务任务号 | 提交信息正则匹配内部任务号（形如 `PROJ-123`），用于统计需求关联率 | **整条指标删除**。它只对特定研发流程有意义，公开仓库无法复现，留着只会让读者困惑 |
| 内部仓库名 / 路径 | 硬编码的内部项目路径 | 改为命令行参数 `report <repo>`，任意仓库可跑 |
| 组织内 AI 工具名 | 只匹配某个自研 agent 的 trailer | 改为 12 个通用工具的匹配表 + `--ai-pattern` 扩展 |
| 真实统计数字 | 内部报告里的具体份额、返工率 | 仓库里只有 `examples/demo-report.md`，由 `demo` 子命令用**合成提交**生成，每台机器跑出来都一样（固定 seed） |
| 人名 / 邮箱 | 提交作者列表 | 报告只输出「作者数量」，不输出任何作者标识；demo 里的作者是 `dev-a` / `dev-b` |
| 规格文档统计 | 关联到内部 change 目录的结构化数据 | 删除。这是内部流程特有的，不属于本工具的能力边界 |

## 三、被保留但泛化的内容

- **指标定义**：文件数/行数分位、模块跨度、测试占比、返工率——这些是通用工程度量，不含业务信息。
- **窗口对比方法**：等长时间窗 + 基线窗口，是方法论层面的东西，可以公开。
- **代码气味清单**：`console.log`、空 catch、`as any`、`@ts-ignore` 等，属于通用实践。

## 四、发布前自检清单

- [ ] `git log --format='%an <%ae>' | sort -u` —— 确认没有真实同事姓名/邮箱
- [ ] `git log --format=%B | grep -Ei '内部|保密|confidential|PROJ-[0-9]+'` —— 应为空
- [ ] `grep -rniE '内部|保密|confidential|proprietary' . --exclude-dir=.git` —— 应为空
- [ ] 带上你自己的关键词再跑一遍扫描门（**真实雇主名/域名只走环境变量，不写进仓库**）：
      `CORP_PATTERNS='<雇主名>' CORP_EMAIL_DOMAINS='<公司域名>' INTERNAL_ID_PATTERN='<工单前缀>' ./scripts/scan-sensitive.sh`
- [ ] `examples/` 下只有 `demo-report.md`，且其内容来自 `ai-attrib demo`
- [ ] 提交邮箱是个人邮箱，不是公司邮箱（见下）

## 五、提交邮箱隔离（最容易翻车的一步）

`git config --global user.email` 如果指向公司邮箱，那么**每一个 personal 仓库的每一个提交都会泄露你的雇主**。
在发布前，至少对本仓库设置局部身份：

```bash
cd ai-code-attribution
git config user.name  "你的名字"
git config user.email "你的个人邮箱"
git config --get user.email   # 确认输出不是 @<公司域名> 之类
```

更稳妥的做法是全局拆成两套：个人目录下用个人身份，工作目录下用公司身份，靠 `includeIf` 按目录切换。

## 六、如果将来要接真实数据

不要在仓库里提交真实报告。需要展示「真实效果」时：

1. 选一个**公开**仓库（例如某个知名开源项目）跑一遍；
2. 把生成的文件放进 `examples/`，并在 README 注明数据来源与采集时间；
3. 任何人用同一条命令都能复现这份数字——这是唯一可接受的「真实数据」展示方式。
